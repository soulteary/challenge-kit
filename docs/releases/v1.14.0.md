# challenge-kit v1.14.0

This release lets the key of the HMAC code hasher be changed while challenges
created under another key are still outstanding. `NewHMACCodeHasher`, the
stored format, `ManagerInterface` and the existing signatures are unchanged,
and there is no new dependency.

## Added

- `NewHMACCodeHasherWithPrevious(key, previous...)`: a `CodeHasher` that
  writes with `key` and verifies under `key` and under each of `previous`.
- `HMACCodeHasherMaxPreviousKeys` (4): the largest number of previous keys
  accepted.

## Behaviour

- `Hash` computes the stored value under the primary key only. The stored
  value is `hmac-sha256$v1$<base64url MAC>` as in v1.13.0 and carries no key
  identifier.
- `Verify` computes the MAC of the submitted code under every configured key
  and compares each in constant time, with no early exit. A code that matches
  under none of them is a wrong code, as with one key.
- Every key, previous ones included, must be at least
  `HMACCodeHasherMinKeyLen` (32) bytes. All keys are copied.
- A previous key equal to the primary key or to an earlier previous key is
  accepted and has no effect.
- `Config.CodeHasherVerifyOnly` works as before: `Create` stores Argon2 hashes
  and `Verify` accepts values written under any of the keys.

A previous key is as sensitive as the primary one for as long as values
written under it exist. Keep it out of the Redis instance that holds the
challenges, and remove it once those challenges have expired.

## Upgrade and rollback

```sh
go get github.com/soulteary/challenge-kit@v1.14.0
```

No change is needed when upgrading from v1.13.0, and no data migration is
required. A caller that does not use the new function behaves as in v1.13.0.

To change the key of instances that restart one at a time, with A the current
key and B the new one:

1. Run every instance with key A and previous key B. What is stored does not
   change; every instance learns to verify B.
2. When all instances run that way, run every instance with key B and
   previous key A. Instances still in stage 1 verify the values the switched
   ones write, and the switched ones verify values written under A.
3. No sooner than one `Config.Expiry` after the last instance left stage 1,
   run every instance with key B and no previous key.

Going straight from key A to "key B, previous A" is safe only when all
instances restart together. An instance that still has only A counts a
correct code for a challenge written under B as a wrong code, which consumes
an attempt.

To go back during stage 2, return every instance to the stage 1 settings, and
remove B one `Config.Expiry` after the last instance stopped writing with it.

Rolling back to v1.13.0 needs no data change. A v1.13.0 instance has one key:
finish or undo a key change before rolling back, and revert callers that use
`NewHMACCodeHasherWithPrevious` first.

For the two-stage change from Argon2 to a hasher, see the
[v1.13.0 notes](v1.13.0.md).
