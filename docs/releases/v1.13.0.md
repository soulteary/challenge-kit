# challenge-kit v1.13.0

This release lets a caller replace how codes are hashed for storage, and ships
an HMAC-SHA-256 implementation. With the default configuration codes are
hashed with Argon2 and stored exactly as in v1.12.0, and `ManagerInterface`
and the existing signatures are unchanged. There is no new dependency.

## Added

- `Config.CodeHasher` and the `CodeHasher` interface: replace the built-in
  Argon2 hashing of codes. Nil, the default, keeps the Argon2 behaviour and the
  stored format of v1.12.0.
- `NewHMACCodeHasher`: a `CodeHasher` that stores
  `hmac-sha256$v1$<base64url MAC>`, an HMAC-SHA-256 over a fixed label, the
  challenge ID and the code. The key must be at least 32 bytes
  (`HMACCodeHasherMinKeyLen`).
- `Config.CodeHasherVerifyOnly`: with a `CodeHasher` set, `Create` keeps
  storing Argon2 hashes while `Verify` accepts both forms.
- `ErrCodeHasher` and `ErrCodeHashFormat`.

## Behaviour with a hasher set

- `Create` stores what the hasher returns. It refuses a hasher value that is
  empty or in a built-in Argon2 form, and stores nothing when the hasher
  returns an error.
- `Verify` chooses by the stored value. A value in a built-in Argon2 form is
  compared with Argon2, so challenges created before the hasher was set keep
  verifying until they expire. Any other value is passed to the hasher.
- A hasher error on `Verify` is not a wrong code: the result carries
  `ReasonBackendUnavailable`, the error matches both `ErrCodeHasher` and
  `ErrBackendUnavailable`, and no attempt is consumed.
- Attempt counting, the user lock and the atomic Redis mutations are unchanged.

The HMAC digest is bound to the challenge ID, so equal codes of two challenges
do not produce equal stored values. Its key must not be stored in the Redis
instance that holds the challenges: the point of the scheme is that the stored
values are of no use to someone who can read that Redis only.

## Upgrade and rollback

```sh
go get github.com/soulteary/challenge-kit@v1.13.0
```

No change is needed when upgrading from v1.12.0 with the default
configuration, and no data migration is required.

A manager without the hasher, including every earlier release, cannot verify
the values a hasher wrote: it counts a submitted code for such a challenge as a
wrong code. Change the hasher of a running fleet in two stages:

1. Run every instance with the `CodeHasher` set and `CodeHasherVerifyOnly`
   true. New challenges are still stored with Argon2; every instance can
   verify both forms.
2. When all instances run that way, clear `CodeHasherVerifyOnly` on all of
   them. New challenges are stored by the hasher.

To go back, set `CodeHasherVerifyOnly` again on every instance, wait for the
challenges the hasher stored to expire (at most the configured `Expiry`), and
only then remove the `CodeHasher` or roll back to v1.12.0.

- All instances that verify the same challenges need the same HMAC key.
  Changing the key makes outstanding challenges stored by the hasher fail as
  wrong codes until they expire.
- Rolling back to v1.12.0 needs no data change once no challenge stored by a
  hasher is outstanding. Callers that set the new fields must be reverted
  first.

For the verification and activation guidance that applies to earlier versions
as well, see the [v1.11.1 notes](v1.11.1.md).
