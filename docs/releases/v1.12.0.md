# challenge-kit v1.12.0

This release adds three options for the user lock. With the default
configuration the lock behaviour, Redis key names and TTLs are those of
v1.11.2, and `ManagerInterface` is unchanged.

## Added

- `Config.LockoutThreshold`: the number of challenges a user must exhaust
  (`MaxAttempts` wrong codes each) within `LockoutDuration` before the user is
  locked. `0` and `1` lock on the first exhausted challenge, as before. With a
  higher value an exhausted challenge is still refused with `ReasonLocked`, but
  the user's other challenges keep working until the threshold is reached.
- `Config.LockCounterPrefix` (default `otp:lockcount:`): the Redis key prefix
  for the record of exhausted challenges. It is used only when
  `LockoutThreshold` is above `1`.
- `Config.LockIdentity`: maps a user ID to the identifier used in lock and
  counter keys, for example a keyed digest, so the raw user ID need not appear
  in Redis key names. Nil, or an empty result, uses the user ID.
- `Manager.IsUserLockedE` and the `UserLockChecker` interface: report a user
  lock together with the backend error. `IsUserLocked` still answers `true` on
  a Redis error.

## Behaviour with a threshold above one

- Each exhausted challenge is counted once, however often it is probed.
- The window starts with the first exhausted challenge and is not extended.
- A successful verification does not clear the record.
- When the threshold is reached the user is locked for `LockoutDuration` and
  the record is cleared.
- A failure to record an exhausted challenge is returned as
  `ErrBackendUnavailable`.
- The record is one Redis set per user, written by a single-key script.

The lock bounds how long a user is refused; it is not what bounds guessing.
The number of codes that can be tried for a user is the number of challenges
the caller allows to be created multiplied by `MaxAttempts`, so keep a creation
rate limit in the caller.

## Upgrade and rollback

```sh
go get github.com/soulteary/challenge-kit@v1.12.0
```

No change is needed when upgrading from v1.11.2 with the default
configuration, and no data migration is required.

- Raising `LockoutThreshold` adds keys under `LockCounterPrefix`. They expire
  within `LockoutDuration`.
- Setting or changing `LockIdentity` moves locks to new key names. Locks stored
  under the previous identifiers are no longer read and expire within
  `LockoutDuration`; a lock in force at that moment is not carried over.
  Instances that run with different `LockIdentity` settings do not share
  locks, so change it on all instances together.
- Rolling back to v1.11.2 needs no data change. Callers that set the new
  fields or call `IsUserLockedE` must be reverted first. Counter keys left
  behind expire on their own.

For the verification and activation guidance that applies to earlier versions
as well, see the [v1.11.1 notes](v1.11.1.md).
