# challenge-kit v1.11.1

This patch selects `secure-kit/v2` v2.1.4 and publishes the current verification
and activation documentation corrections merged after v1.11.0. Public APIs,
Argon2 challenge hashes, Redis key formats, namespaces, TTLs and lockout behavior
remain unchanged. The secure-kit update fixes masking helpers; challenge-kit's
random-code and password-hashing use does not change its wire or stored format.

## Verification and activation guidance

- Strict activation remains opt-in: `RequireActiveVerification` defaults to
  `false`. Pending strict challenges return `ReasonNotActive` without consuming
  an attempt. Follow the existing disjoint-namespace migration before enabling
  strict mode; older readers must not access strict records.
- Binding mismatches consume no attempt. Ordinary negative verification results
  carry both a result and an error; inspect `Reason` after handling retry and
  backend failures rather than terminating the process on every error.
- A backend failure never reports verification success, but a write may already
  have committed. Do not restore attempts or assume an OTP remains unconsumed.
- Expiring leases bound work; snapshot comparisons protect committed mutation.
  Strict activation uses a multi-key script and requires matching Redis Cluster
  hash tags. Lua runtime errors can retain prior writes; existing pending-record
  recovery and lost-reply guidance still applies.

## Test reliability

The concurrent wrong-code regression now counts committed outcomes rather than
assuming every call spends an attempt. It retries only documented lock contention
within a bounded context, checks the persisted counter and actual Redis user lock,
and uses a code guaranteed to differ from the generated OTP. No production lock
settings, verification behavior or CI thresholds are changed.

## Upgrade and rollback

```sh
go get github.com/soulteary/challenge-kit@v1.11.1
```

Rebuild callers. No additional namespace or data migration is required when
upgrading from v1.11.0 with the same activation policy. Keep Redis data and TTLs;
do not flush challenges, active indexes or lockout state during rollout.

For rollback, restore the application's pre-upgrade `go.mod` and `go.sum` and
rebuild. Downgrading only challenge-kit does not necessarily downgrade its
transitive secure-kit requirement. For a minimal consumer:

```sh
go get github.com/soulteary/challenge-kit@v1.11.0 github.com/soulteary/secure-kit/v2@v2.1.3
go list -m github.com/soulteary/challenge-kit github.com/soulteary/secure-kit/v2
```

Check the whole selected module graph before assuming a dependency was restored;
other modules may require a newer version. Existing v1.11.0 challenge state
remains compatible. Rollback does not undo consumed codes or expired records.
Enabling strict mode from an older compatibility-only deployment still
requires its existing namespace migration in either patch version.
